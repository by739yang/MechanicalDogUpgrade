### 为什么钉住 `espressif32@6.5.0`

本机 `~/.platformio/packages/framework-espidf` 是 **ESP-IDF v5.1.2**，正对应 `espressif32@6.5.0`。
钉住版本可以复现，并避免重复下载框架包。

### 为什么用 legacy `driver/i2c.h`

IDF 5.1.2 **没有**新版 `driver/i2c_master.h`（IDF 5.2 才引入）。
因此 `bsp_i2c.c` 使用 legacy master API（`i2c_param_config` / `i2c_master_write_to_device` /
`i2c_master_write_read_device` / `i2c_master_read_from_device`）。
将来升级到 IDF ≥ 5.2 时再迁移到新 API。

## 4. 上电行为

**上电不会让任何舵机动作**（全部通道被置为「无脉冲」= 舵机松力）。自检依次做六件事：

1. 从 NVS 载入配置（没有 / 损坏 / 版本不符 → 用默认值并打印原因）
2. I2C 总线恢复（发 9 个时钟脉冲，解开从机把 SDA 拉死的情况）
3. **位操作扫描**全总线 112 个地址，核对 `0x40` / `0x41` 是否都在
4. 安装 I2C 驱动，定点探测 `0x40` / `0x41` / `0x70`
5. 初始化两片 PCA9685（50 Hz），并把**全部通道置为「无脉冲」**
6. 回读 `MODE1` / `PRESCALE` 并打印，与 MicroPython 版实测值（`0x21` / `122`）对照

然后启动串口控制台等待命令。

> 为什么扫描要用**位操作**而不是 I2C 驱动：IDF 5.1.2 的 I2C 驱动把事件等待时间
> **硬性下限钉在 1000 ms**（`I2C_CMD_ALIVE_INTERVAL_TICK`），所以探测一个**不存在的地址**
> 每次都要等满 1 秒 —— 112 个地址就是 112 秒。位操作扫描没有这个下限：
> **112 个地址 21 ms 扫完**。详见 `../问题与解决记录.md` 的 P-12。

### 步骤 7：舵机输出层 + 运动模块（P2）

`servo_out_init()` 把 12 路缓存初始化为"无脉冲"（与驱动刚做过的 `all_off` 一致），
`motion_init()` 建好锁但**不启动控制任务**。

⇒ **上电永远不会让舵机动。** 必须显式 `stand` + `motion start` 才会输出脉宽。

## 5. 串口控制台命令

| 命令 | 说明 |
|---|---|
| `help` | 显示帮助 |
| `scan` | 重新扫描 I2C 总线并核对 |
| `status` | 回读两片板的 `MODE1` / `PRESCALE` |
| `freq <hz>` | 设置频率（24..1526，默认 50） |
| `set <board> <ch> <us>` | 单通道输出指定脉宽（限制 500..2500 µs） |
| `deg <board> <ch> <0..180>` | 按 MicroPython 的换算输出对应脉宽 |
| `all <board> <us>` | 该板全部 16 路输出同一脉宽（⚠️ 会同时驱动所有舵机） |
| `off <board>` | 该板全部通道无脉冲（松力 / 安全态） |
| `sweep <board> <ch> <from> <to> <step> <delay_ms>` | 慢速往返扫动，总时长上限 30 s |
| `raw <board> <reg_hex>` | 读一个寄存器（调试） |
| `cfg` | 列出全部配置项与当前值 |
| `cfg get <key>` | 读一项 |
| `cfg set <key> <value>` | 改一项（越界会**自动限幅**并告诉你改了哪几项） |
| `cfg save` | 保存到 NVS（写前算 CRC） |
| `cfg load` | 从 NVS 重新载入 |
| `cfg reset` | 恢复出厂默认**并擦除** NVS |
| `cfg defaults` | 只把当前内存里的值恢复为默认（不写 NVS） |

`board`：`0` = 0x40（左半身），`1` = 0x41（右半身）。

### 配置项（`cfg` 支持的 key）

- **中位角**：`c1_hip` / `c1_knee` / `c1_shank` …… `c4_*`（腿1..腿4 各 3 个，共 12 项）
- **几何**：`r_h` / `r_l1` / `r_l2` 等（机身与腿长）
- **姿态**：`h_goal` / `pit_goal` / `rol_goal` 等
- **步态**：`faai` / `walk_faai` / `gyro_p` / `ma_case` / `joy_fwd_sign` / `cal_leg_sel`
- **机械臂**：`arm_*`
- **网络**：`ap_ssid` / `ap_password`

> `cfg set` 的越界值不会被拒绝，而是被**限幅**到合法区间并提示 —— 这样在串口调试时
> 不会因为打错一个字就丢掉整条命令。限幅规则在 `app_config.c` 的 `app_config_validate()`。

### P3：控制链与步态

`app_chain.c` 把 `control_chain_tick()`（= 原版 `mainloop()` 的一帧）接到运动任务上。

**两种控制模式**：

| 模式 | 角度从哪来 | 速率限制 | 用途 |
|---|---|---|---|
| `pose` | 直接用给的 12 路角度 | ✅ 有 | 标定、单通道测试 |
| `chain` | `control_chain_tick()` 算出来 | ❌ **刻意没有** | 站立、走路 |

> **为什么 CHAIN 模式不加速率限制**：步态轨迹本身就是被 golden **逐位验证过**的东西，
> 再限速等于改了轨迹、与原版不等价。安全靠别的手段：命令级 `spd` 范围、
> `estop`、超时停车、停止时松力。

**⚠️ 链有自己的节拍，不是 100 Hz**：默认 **65 ms**。

原版每轮主循环 `t += speed`（`speed = 0.065`），跑完一个周期要 `Ts/speed ≈ 15.4` 轮；
而原版主循环被网页轮询拖到 **35~120 ms 一轮**，`15.4 × 65 ms ≈ 1 s`
⇒ **`speed` 是照着 ≈65 ms 的循环周期调出来的**。在 100 Hz 里直接跑会 **6.5 倍速**。

⇒ 推导：**链节拍周期（秒）= `speed`**，这样 `Ts = 1.0` 才真的等于"一个周期 1 秒"。
运动任务仍跑 100 Hz（急停响应、将来 P4 的 IMU 闭环），只在链的节拍上推进；
其余帧重新下发同一组角度 —— 因为 `servo_out` 只写变化的通道，**这些帧的 I2C 开销是 0**。

**"停止走路" ≠ "松力"**：

- `jog 0 0 0` 或 `stand` → 狗**站着**（控制链持续输出站姿脉冲）
- `motion stop` / `estop` → 12 路**无脉冲**，狗**趴下**（松力）

### ⚠️ `stand` 与 `stand direct` 是两个不同的姿态

| | 走哪条路 | 是什么 |
|---|---|---|
| `stand` | 完整控制链（`cal_ges` → IK → `servo_output`） | **原版真正的站姿** |
| `stand direct` | `servo_output()` 的 else 分支（12 路 = 中位角） | **标定用站姿**，不是正常站立的样子 |

两者差别很大（大腿/小腿差 40~110 个占空比，右腿尤其明显）。
逐通道对照表见 `../硬件实物核对清单.md` **阶段 E8**。

### ✅ 站立验证怎么做（真机，**USB 就够，不用电池**）

```
readback            # 1. 确认 12 路都是 ON=0 OFF=4096（无脉冲/松力）
chain               # 2. 控制链状态：应为 POSE 模式、目标 H=81 PIT=0 ROL=0 X=18
stand               # 3. 切到 CHAIN 模式并下发站立命令
motion start        # 4. 启动控制任务
#     等 1 秒让姿态 slew 收敛
readback            # 5. 期望值 = golden/control_chain.csv 第 1 行：
#                      333 402 424 311 434 446 320 199 181 347 169 143
estop               # 6. 收尾松力（否则插电池那一刻舵机会绷住）
```

第 5 步的 12 个数字与 golden **完全相同**，就说明整条链在真机上跑对了：
**配置 → 大狗缩放层 → 姿态 slew → 重心分支 → `cal_ges` → IK → 映射层 → I2C → 芯片**。
这是 P3 最有说服力的一次验证。

> ⚠️ **不插电池时舵机不会动，但寄存器照样会写** —— 所以上面这套**不需要电池**。
> ⚠️ 默认 `motion timeout` 是 10 s：10 秒不发命令它会自己松力停车，
> 想让它一直站着就 `motion timeout 0`。

### 连续运行测试怎么做（注意：不插电池时舵机不会动）

```
motion timeout 0       # 关掉超时，否则 10 秒没人理它就自己停了
stand                  # 只是把"目标角度"设成站姿
motion start           # 启动控制循环并开始写寄存器
# 然后**不要**发任何命令，用只监听、不复位的脚本观察：
#   python ..\diagnostics\monitor_serial.py COM4 640 run_10min.log --check-reboot
motion stat            # 结束后看 ticks / 周期 / 超期次数
estop                  # ★ 收尾：把 12 路置回松力，别让它停在"绷着"的状态
```

`monitor_serial.py` 刻意不碰 DTR/RTS（那会复位板子），所以能在板子连续运行时观察，
`--check-reboot` 还会报告中途有没有出现启动横幅。

> ⚠️ **不插电池时舵机不会动**（PCA9685 逻辑电走 USB，舵机 V+ 走电池）。
> 所以这个测试验的是**固件连续运行的稳定性**（不重启、不看门狗、周期不退化），
> **不是**"狗站了 10 分钟"。后者需要插电池 + 架空。

> ⚠️ **收尾一定要 `estop`。** 测试结束时控制任务会停在"输出站姿脉冲"的状态，
> 此时若直接插电池，**12 个舵机会立刻绷到站姿**。插电池前先 `estop`（或 `lg off`），
> 让 12 路处于无脉冲，狗就是软的，想怎么摆弄都行。

### 单写者不变式（为什么 `lg` 会被拒绝）

控制任务在跑的时候**只有它写舵机**。否则两个任务会交错写同一条 I2C
（迁移表 §8.5 的要求）。所以 `lg` / `lgtest` / `set` / `deg` / `all` / `off` 这类
直接写寄存器的命令在控制任务运行时会被拒绝：先 `motion stop` 或 `estop`。

总线本身在 `bsp_i2c` 里有**递归互斥锁**，每次传输内部自动加锁；
缓存一致性靠"单写者 + `servo_out_invalidate()`"保证。

>
> 只插 USB（不插电池）时，**舵机 V+ 没有电，舵机一定不会动**。

> | 控制循环的周期、抖动、超期 | `motion stat` | ❌ 不需要 |
> | 急停 / 超时是否真的把 12 路置为松力 | `estop` + `readback` | ❌ 不需要 |
> | 舵机到底转不转、往哪转 | 眼睛看 | ✅ **需要** |
> | 逻辑通道 0~11 对应哪个物理关节 | `lgtest` + 眼睛看 | ✅ **需要** |
> | "无脉冲"是否真的没有力矩 | 手推一下关节 | ✅ **需要** |
> | 装上负载能不能站住 | 计时 + 看 | ✅ **需要** |

### 分层与可测试性

`control/` 里全部是**纯函数、零 IDF 依赖**，所以能用宿主 gcc 直接编译并与
MicroPython 参考逐数值对照（`../tools/golden/`）。

`app_config.c` 同样零 IDF 依赖：持久化后端是**注入**进去的函数指针表
`app_cfg_store_t`，宿主机塞 RAM 假后端、真机塞 NVS 后端，上层逻辑一行不改。
这是 P1 能在**不插板子**的情况下验完的主要原因。

`servo_map.c` 也刻意不 include 驱动头文件（那会拉进 `esp_err.h`，宿主就编不了了），
代价是板地址常量写了两份 —— 由 `servo_out.c` 里的 `_Static_assert` 保证一致，
**编不过**好过**悄悄写错板子**。

后续阶段按迁移表增加 `arm/`（arm_control）、`comm/`（wifi / http_server / websocket / telemetry）。

## 9. 已知与 MicroPython 版的差异（有意保留，便于对照）

1. **PRESCALE 不减 1**：MicroPython 的 `PA_SERVO.py` 用
   `prescale = int(25000000/4096/freq + 0.5)`（50 Hz → 122），
   而数据手册是 `round(25000000/(4096*freq)) - 1`（50 Hz → 121）。
   本驱动默认**复刻 MicroPython**（写 122），以保证脉冲一致。
   改 `DRV_PCA9685_PRESCALE_LEGACY` 为 `0` 即切换为手册公式。
2. **占空比满量程用 4095 而非 4096**：与 MicroPython 的 `_us2duty()` 一致。
3. **角度→脉宽换算** `drv_pca9685_us_from_degrees_ref()` 也是复刻 MicroPython
   （含整数截断），专供 P1 做 Python/C 对照。

## 10. P2 的性能账（P3 要接着算）

I2C 跑 100 kHz，一次 PCA9685 通道写 = 地址 + 寄存器 + 4 字节数据
≈ 6 字节 × 9 bit × 10 µs/bit ≈ **0.5 ms**。

| 情况 | 每帧 I2C 写 | 每帧耗时 | 占 10 ms 周期 |
|---|---:|---:|---:|
| 站姿稳态（12 路都不变） | **0** | **40 µs**（实测） | 0.4% |
| `stand` 逼近过程中 | 12 | ~6 ms（实测最长 7674 µs） | 60% |
| P3 的 TROT（12 路每帧都变） | 12 | ~6 ms | **60%** ⚠️ |

⇒ **"只写变化的通道"是 P2 能站住的关键**，稳态几乎不花 I2C 时间。
但 P3 一开始跑步态，12 路每帧都会变，60% 的周期预算花在总线上，
抖动余量会很小。

**下一步的杠杆（先测再动）**：把 I2C 提到 **400 kHz**（PCA9685 支持到 1 MHz，
总线上只有两片器件），同样的写会降到约 1.5 ms/帧。
这**不影响 PWM 输出**（只影响总线时序），但要先量出 P3 的实际抖动再决定，
不要提前优化。

**为什么不现在改**：P2 是第一次让舵机真的通电动作，这一轮刻意保持
100 kHz（与 MicroPython 版一致），一次只改一个变量。
